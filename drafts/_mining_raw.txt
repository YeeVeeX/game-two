==================== kethral ====================
--- version_identity ---
This kethral/ directory is the SECOND and largest Kethral prototype in the "Game On(e)" workspace (a pygame-ce game, distinct from the earlier prototype/ dir and the never-started kethral_v2/ and project/ Godot dirs). Per WORKSPACE_STATUS.md:4 (dated April 2, 2026) it was at "Phase 16 Complete" with 1,364 tests passing across 40+ test files; the code on disk has clearly moved further — kethral/game.py contains explicit "Phase 22B" comments (kethral/entities/player.py:230-235, 701-702, 724) and the docs/ dir contains architecture docs up through PHASE22_IMPLEMENTATION_PROMPT.md and PHASE21_IMPLEMENTATION_PROMPT.md, so the status doc is several phases stale relative to the actual code. It is a data-driven (40+ JSON files under kethral/data/), event-bus-driven (kethral/core/event_bus.py) pygame-ce action RPG prototype with a single 3,997-line game.py orchestrator (verified via `wc -l`, NOT the 2,663 lines claimed in WORKSPACE_STATUS.md:44 — the god-object problem this rebuild's own CLAUDE.md cites as a Kethral failure mode is measurably worse in this version than documented). Two later, more ambitious redesigns are documented in this same directory but were never implemented in code: KETHRAL_V2_ARCHITECTURE.md (a clean-slate Python/pygame-ce rebuild plan) and GODOT_MIGRATION_PROMPT.md (a subsequent pivot away from Python to Godot 4.x, citing pygame's inability to produce real pixel art) — no kethral_v2/ directory exists anywhere in the repo.
--- movement_model ---
Grid-stepped with smooth pixel interpolation on top — NOT free pixel movement. TILE_SIZE = 32 (kethral/world/tilemap.py:15, kethral/entities/base_entity.py:16). Entities (kethral/entities/base_entity.py:19-236) hold a logical integer (grid_x, grid_y) tile position that updates instantly on move_to(), plus a separate float (visual_x, visual_y) pixel position that smooth-steps (cubic ease, `3t²-2t³`) toward the new tile over a duration (kethral/entities/base_entity.py:74-144). All game logic (collision, combat range, AI, zone transitions) operates on the integer grid coordinates only — the float visual position exists purely to animate the walk between tiles. Player move duration = `1.0 / base_speed_tiles_per_sec` (default base_speed=4.0 tiles/sec → 0.25s per tile); a run_speed_tiles_per_sec=6.0 stat is defined in defaults but no code path switching to it was found in the sampled files (kethral/entities/player.py:40-41,105-106). Diagonal moves cost `duration * 1.414` (√2 scaling) (kethral/entities/player.py:281-282). Held-key behavior: while a move is interpolating (`is_moving` true), a new directional input is captured into a single-slot `_input_buffer` and fired the instant the current move completes (kethral/entities/player.py:239-298) — gives continuous-feeling movement on a held key without needing per-frame move requests. Collision is tile-based: `TileMap.is_passable(x,y)` checks membership in a passable-TileType set (FLOOR, DOOR, ZONE_TRANSITION, SPAWN_POINT, NPC_POSITION, GRASS, BUSH, FLOWER, PATH, PUZZLE_PEDESTAL) (kethral/world/tilemap.py:40-52,89-91); an optional `blocked_tiles` frozenset additionally blocks tiles occupied by enemies (kethral/entities/player.py:275-277). Dodge is a special multi-tile grid move (up to dodge_distance_tiles, default 2) that scans for the farthest passable tile in a direction at half normal per-tile duration, and can cancel/override an in-progress move (kethral/entities/player.py:581-676).
--- world_structure ---
Four zones exist in code: town ("Solthrekan," 40x30 tiles, hand-placed via direct tile calls in kethral/world/town_gen.py:17-80), dungeon ("Threketh," BSP-generated, 80x60 tiles by default via kethral/world/dungeon_gen.py:20-21,118+, corridor width 3, room size 10-18, seeded and overridable by JSON presets at kethral/data/world/presets/{default,sparse,dense}.json), forest (kethral/world/forest_gen.py — a chain of discrete named "rooms" each ~20x15 tiles per forest_gen.py:170, loaded from JSON templates under kethral/data/templates/forest/*.json: forest_edge, verdant_canopy, ancient_grove, crystal_hollow, thornweave_thicket, forest_depths, volcano_gate — 7 rooms navigated door-to-door rather than one contiguous map), and oramek (coastal zone, kethral/world/oramek_gen.py, procedurally generated and seeded like the dungeon). All zones share one TileMap class (kethral/world/tilemap.py:55-137): a flat 2D grid of TileType enum values, a `rooms` list of rects (fog-of-war/discovery), and a `transition_targets` dict mapping specific (x,y) coordinates to a target zone string (e.g. "dungeon", "forest", or "forest_room:<name>" for intra-forest door transitions) (tilemap.py:70-76; managers/world_manager.py:219-266). WorldManager (kethral/managers/world_manager.py:25-542) centralizes zone state: one TileMap per zone, a `current_zone` string, transition detection when the player's tile equals ZONE_TRANSITION/DOOR, and a `_transition_cooldown` to prevent instant teleport ping-pong. Forest rooms are swapped out wholesale (`load_forest_room`) rather than being sub-areas of a single big map, so "forest" is structurally a string of discrete rooms linked by single DOOR tiles, closer to Zelda-style dungeon rooms than an open overworld. A cosmetic-only Phase 21C-02 addition (tilemap.py:143-306, MultiLayerTileMap) layers deterministically-hashed decoration (cracks/moss/scorch, arches/bridges) on top of each zone's base TileMap — no added real geometry or collision. Net effect: the world is a small hub (town) plus 3 separately-generated zones reached through single fixed transition tiles — not one open, contiguous space. This directly explains why "the arena is not what I intend" would be a valid owner complaint if his rebuild goal is more open/connected: KETHRAL_V2_ARCHITECTURE.md §7 documents a much larger 5-biome archipelago hub-and-spoke with unlock-gated connections between Solthrekan and Verdant Reach/Threketh Tunnels/Ashenmere/Kurvorn Ruins/The Resonance, but this is planning-only — confirmed no kethral_v2/ directory exists anywhere in the repo (`ls` of the parent dir shows only kethral/, prototype/, project/(Godot)), so none of that redesign was ever implemented.
--- feel_and_fun ---
The loop both code and docs center on is: town (safe — NPC dialogue/shop/crafting) → venture into dungeon/forest/oramek (stamina-gated light/heavy/spin/ranged attacks, combo chains, parry, positional damage, charge-based heavy) → death (drops gear, respawn in town) → repeat with more knowledge/gear. WORKSPACE_STATUS.md frames "Phase 16" as when combat got real juice (damage numbers, screen shake, swing overlays, differentiated enemy AI, procedural SFX, dialogue, bestiary) — i.e. the team's own sense of "this feels like a game" arrived from combat-feel polish layered onto an already-large systems base, not from new mechanical depth. game.py's 70+ handler methods (hitstop via _on_entity_died_hitstop/_on_damage_dealt, breathing-phase camera effects, weapon switching, spell casting, boss detection, all wired directly into the 3,997-line orchestrator) show the "feel" was achieved by wiring many small feedback systems individually into the god-object loop rather than through a lean event-driven core — exactly the architectural failure mode this rebuild's own CLAUDE.md calls out (orchestrator cap of ~300 lines) and that KETHRAL_V2_ARCHITECTURE.md itself tries to fix via its "No Invisible Code" rule and integration-first development principle. Tellingly, KETHRAL_V2_GAP_ANALYSIS.md (written by the same team reviewing their own V2 design, dated the same day as the architecture doc, 2026-04-05) independently flags that fun combat still depends on things NOT yet present even in the redesign plan — encounter composition (multiple enemies fighting together tactically), player hit-stun/i-frame recovery specifics, a concretely-numbered stamina economy, and per-enemy telegraph variety — suggesting the team itself considered combat feel incomplete/monotonous even at Phase 21+ despite the large feature list.

kethral_v2 is an abandoned, incomplete THIRD restart attempt — a from-scratch clean-slate architecture rewrite that was being built concurrently with (not after) the tail end of kethral/'s Phase 21-22 development, and it appears to have never been committed to git. Evidence: (1) `git ls-files | grep kethral_v2` in the "Game On(e)" repo returns zero results and `git status` shows the entire kethral_v2/ tree as untracked (`??`), while kethral/ has deep commit history (Phase 14-17 commits visible via `git log --oneline`). --- movement_model ---
Grid-stepped movement, NOT free continuous pixel movement — despite module docstrings claiming otherwise. Tile size is 32px (kethral_v2/settings.py:12, TILE_SIZE=32). Player.handle_input() (entities/player.py:575-676) reads held WASD/arrow keys into an intent vector _input_dx/_input_dy each in {-1,0,1} (diagonals representable since both axes can be set). Player.update() (entities/player.py:838-851) then calls EntityBase.request_grid_move(dx,dy,tile_renderer) (entities/entity_base.py:154-186), which — only if not already mid-move (is_grid_moving guard) and the destination tile is walkable via a single tile_renderer.get_tile_at() lookup (TILE_WALL=1 blocks) — commits target_grid_x/target_grid_y and sets is_grid_moving=True. EntityBase.update_grid_movement(dt) (entity_base.py:121-152) then visually interpolates pos_x/pos_y from the old grid cell to the new one over 1/move_speed seconds; move_speed = PLAYER_GRID_SPEED = 4.0 tiles/sec (settings.py:183), i.e. one 32px step takes 0.25s. Held keys queue the next tile-step the instant the current one finishes — so holding a direction produces smooth continuous walking, but position is always grid-locked between steps, never free sub-tile placement (except during the tween itself). Enemies use the identical primitive at ENEMY_GRID_SPEED=3.5 tiles/sec (entities/enemy.py patrol/pursue call request_grid_move one tile at a time, e.g. enemy.py:565,630). A vestigial continuous-pixel-movement code path still exists in the file (PLAYER_SPEED=200px/s at settings.py:32; _move_x/_move_y and _update_facing() at player.py:679-716) but is dead for actual displacement — those fields only mirror the grid-input direction for combat-routing (`is_moving` checks) and animation-clip selection. The one genuinely continuous-pixel motion is knockback after taking a hit (player.py:757-788): a decelerating velocity (v0 = sqrt(2*KNOCKBACK_DECEL*KNOCKBACK_DISTANCE_PX)) applied per-axis with independent wall collision via a 4-corner, 2px-inset AABB check (_collides_at, player.py:853-887 and the identical pattern in enemy.py:742-773).
--- world_structure ---
Exactly one hand-authored JSON room, no procedural generation, and no map/zone-transition code exists despite the architecture doc's ambitions. data/rooms/cantero_hub_01.json defines a single 20x15-tile room ("Solthrekan South Gate") with one "ground" tile-type grid (0=floor,1=wall), a player_spawn coordinate, 5 light_sources (torch/ambient_glow presets), and 5 particle_emitters (ember/dust). data/biomes/cantero.json supplies that one biome's palette/tileset/ambient-light/music config. core/data_manager.py's DataManager recursively loads every JSON file under data/ keyed by its relative path (architecturally ready for many rooms/biomes), but only these two content files exist in the repo. game.py's Game.__init__ (lines 80-91) hardcodes loading "rooms/cantero_hub_01" as the only room, and hardcodes spawning exactly 2 Ravager enemies at fixed pixel coordinates (game.py:104-109, comments "upper-left open area" / "lower-right open area"). There is no room-loading API called anywhere else, no second room, and no world map — directly matching the CLAUDE.md scope-contract phrase "one arena room." This is a stark contrast to kethral/KETHRAL_V2_ARCHITECTURE.md's plan for a 5-6-biome "Thalumari" archipelago with dozens of hand-crafted room-pool variants, 6 town districts, and zone-transition dithering — none of that has corresponding .py implementation anywhere in kethral_v2 (its actual module tree is only core/, entities/, systems/{combat_system,input_manager}, rendering/, tools/ — no world/, ui/, ai/, or any of the dozen manager modules the architecture doc lists under systems/).
--- feel_and_fun ---
The loop as actually built: walk (grid-stepped, 8-directional) into the single Cantero room containing two patrolling Ravagers, get spotted (aggro range 192px), fight with a one-button (J) light/heavy/spin attack router plus a K-key parry (perfect parry = expose + reposition-behind + 2.5x counter), chain L-L-L/L-L-H combos for bonus damage, and watch kills play a 40-frame dissolve (alpha fade + vertical squish) with camera shake — then nothing: no death/respawn, no second room, no title menu beyond ESC-pause, no persistence. Almost all of the engineering effort visible in the code is combat-feel "juice" (frame-counted hitstop 3-7f, camera-shake presets, slash-arc VFX so attacks are visible, positional-damage colored arcs/text, floating damage numbers, knockback physics) and rendering polish (BLEND_MULT per-pixel lighting with flickering torches, a biome-directional PlanarShader for entity sprite shading, 2.5D oblique wall tiles with AO shadow strips, entity ground shadows) — a direct, literal pursuit of the "No Invisible Code" rule stated in kethral/KETHRAL_V2_ARCHITECTURE.md §1.3 ("Every commit must change what the player sees, hears, or feels"). Numerically it even reuses exact values from that doc (e.g. CAMERA_SHAKE_CONFIG in settings.py:79-84 matches §3.7's amplitude/duration/decay tables verbatim). What it deliberately does NOT attempt yet is any of the RPG breadth (skills, mentors, districts, crafting, quests, dialogue, inventory, codex, multiple biomes/enemies, audio) that the same architecture doc spends most of its 1500 lines designing — kethral_v2 reads as "get the combat feel right first, in one tiny room," a vertical-slice-of-a-vertical-slice that stalled before expanding.
