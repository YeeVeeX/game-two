## Refuted (recorded so implementation review does not re-raise these)

### R1 [moderate/code-fit]
CLAIM: The spec says 'cache infra exists, world.rb:162-170' for home-return flow fields, implying the existing flow_to cache can serve them. But flow_to (line 162) is keyed by creature OBJECTS (with a .tile method); home-return fields must be keyed by static TILE COORDINATES. The existing API cannot serve tile-keyed lookups without a wrapper or a parallel cache. An implementer trusting this claim would discover the mismatch mid-build.
REFUTATION: The spec says "cache infra exists, world.rb:162-170" -- it points to infrastructure and an established PATTERN, not a claim that flow_to accepts raw tile coordinates directly. The parenthetical is directionally correct: the FlowField class exists (flow_field.rb:17-37), and the caching pattern for flow fields is proven at those lines. The home-field use case is actually SIMPLER than flow_to (no invalidation needed since home tiles never move). Furthermore, flow_to CAN be reused with a trivial one-line Struct wrapper (HomeTile = Struct.new(:tile)) since Ruby Structs provide value-based hash/eql? equality -- or more naturally, the implementer writes a two-line @home_fields hash following the same pattern. Under Rule 4 (read-before-edit), the implementer reads those 8 lines of Ruby before implementing and the interface is immediately obvious. No reasonable implementer would be "surprised mid-build" by needing to adapt a caching pattern for a simpler case (static keys with no invalidation vs. moving anchors with invalidation). The finding overstates a trivial adaptation into a defect.

### R2 [moderate/code-fit]
CLAIM: The spec says 'Returning humans re-engage normally if a pack body enters aggro_tiles' (section 3), but the beachhead rule (section 4) blocks ACQUISITION of targets within beachhead_tiles of the arrival. A leashed human whose home is near the gate clears its @focus when the target left aggro range. Upon re-engaging, it must ACQUIRE a new focus ? which the beachhead blocks if the pack is near the gate. These rules contradict: re-engagement requires acquisition, and acquisition is blocked by the beachhead.
REFUTATION: The spec is self-consistent. "Re-engage normally" (section 3) means the returning human transitions out of :returning and enters the STANDARD targeting flow ? it does not guarantee acquisition succeeds. The beachhead (section 4) IS part of that standard flow: it conditions acquisition (rules 3-5) on the target's position relative to the arrival tile. A returning human whose home is near the gate that fails the beachhead check simply remains idle at home ? this is the intended safe-zone behavior, not a contradiction. The parenthetical "(a leashed human is dispersed, not invulnerable)" confirms the emphasis is on vulnerability (it can be attacked/woken), not on guaranteeing acquisition. Furthermore, the beachhead's waiver ("a human damaged or taunted by the pack ignores the beachhead for the rest of its life") covers the common gameplay case: any human that was previously in melee combat with the pack was almost certainly damaged and already holds the waiver. The narrow edge case where the "contradiction" fires (focus acquired but pack fled before dealing damage) produces correct behavior ? a human that never actually fought the pack should not re-aggro near the safe zone. The test assertions (line 234-236) list "leash...re-engages" and "beachhead blocks acquisition" as separate coexisting tests, confirming the spec treats them as compatible, not contradictory.

### R3 [moderate/code-fit]
CLAIM: The spec proposes per-tick engaged/pressuring partition (section 2) computed over humans sharing a focus target, but the existing tick loop is single-pass (world.rb:246): each human ticks independently via @ai.tick(h, self). The partition requires knowing ALL humans' focus targets before deciding who is engaged vs pressuring. With a single-pass loop, a human ticked early sets its focus, but later humans haven't been evaluated yet ? the partition can't be computed until all foci are known. The spec doesn't specify that a two-pass structure is needed (pass 1: update all foci; pass 2: partition + execute), which is a structural change to tick_world.
REFUTATION: The spec's Section 2 partition description ("Humans sharing a focus target are partitioned each tick, deterministic (sort by Chebyshev distance, roster-index tiebreak)") IS the two-pass specification ? a group-by-then-sort operation inherently requires collecting all inputs first. Adding an explicit "use two passes" note would be redundant, like annotating "sort the array" with "Note: you need all elements before sorting." Furthermore: (1) focus evaluation (Section 1) is independent per human ? each human's targeting chain depends only on pack body state (positions, HP), which is fully resolved before humans tick (pack AI at line 245, resolve_attacks at line 250); no human's focus depends on another human's focus, so there is no ordering hazard in pass 1; (2) the spec author is the dev of record and implementor ? there is no communication gap where this structural need could be lost; (3) the split is mechanically trivial (one loop becomes two), not a design ambiguity that could produce a wrong implementation. The finding identifies a real implementation detail but it would not change what gets built or decided ? the partition definition already communicates the required structure to anyone implementing it.

### R4 [low/code-fit]
CLAIM: The spec says district arrival is '[1,13]/[2,13]' but [2,13] is from district.json's pack_spawn which is NEVER used during gameplay transitions. The actual arrival tile when entering from the nest is [1,13] only (nest.json transition spawn field, line 37). The [2,13] reference could mislead an implementer computing beachhead or gradient distances from the wrong anchor.
REFUTATION: The finding's premise is wrong. [2,13] is NOT only "from district.json's pack_spawn which is NEVER used during gameplay transitions." Tracing the actual code path: when the player walks from nest to district, `check_transition` calls `arrival_tiles("district", [1, 13])`. That method places the possessed on [1,13] then iterates FlowField::STEPS ([0,-1], [1,0], [0,1], ...) to fill tiles for 3 pack members. Step [0,-1] yields [1,12] (passable, ally 1). Step [1,0] yields [2,13] (passable, ally 2). So the pack's actual arrival positions during a nest-to-district gameplay transition are [1,13], [1,12], and [2,13] ? all three are real arrival tiles computed by `arrival_tiles` at runtime. The spec correctly identifies [1,13]/[2,13] as the district arrival footprint. The coincidence that [2,13] is also in `pack_spawn` is irrelevant; the spec is factually accurate about where the pack physically appears during transitions, and an implementer computing gradient distances from the arrival would correctly use both coordinates.

### R5 [low/code-fit]
CLAIM: The spec claims home fields are 'never invalidated' but enter_zone (world.rb:544) clears @flow_cache = {} on every zone transition. If home fields are stored in @flow_cache (or a parallel cache cleared in enter_zone), they ARE invalidated each time the pack re-enters the district. They'd need recomputation (cheap since targets are static). The 'never invalidated' claim gives a false perf guarantee that could confuse profiling.
REFUTATION: The spec says "home fields are computed once per zone load and never invalidated." The qualifier "per zone load" explicitly acknowledges that computation happens on each zone entry -- the `enter_zone` cache clear at line 544 IS the "zone load" event the spec names, not a separate invalidation. "Never invalidated" refers to the within-zone lifetime: since home tiles are static (`@home_tile` stamped at spawn/respawn and never moved), the `flow_to` cache (lines 162-170) will never trigger a recompute mid-zone (the `entry[:tile] != anchor.tile` check stays false). The performance claim is accurate in context: during the farming loop (the hot path where profiling matters), home fields are zero-cost after their single lazy computation. Zone transitions are infrequent discrete events, not the hot path, and the spec already accounts for them with "per zone load." The finding conflates a zone-boundary recomputation (which the spec explicitly acknowledges) with mid-zone invalidation (which the spec correctly denies).

### R6 [moderate/design]
CLAIM: Pre-registered routing has an unresolved overlap between routes 2 and 4 (spec lines 274-281). Route 2 fires when 'Q3 unmoved + threat FELT (any real positive on Q2/Q4/Q5)' and route 4 fires when 'Threat felt but fights lack scary PEAKS'. Both conditions can be true simultaneously (threat is felt in Q2/Q4/Q5 but fights lack scary peaks). Route 2 says D1b promotes AUTOMATICALLY; route 4 says the Challenger trigger fires. The spec provides no priority ordering or sequencing instruction. The verifier running the sixth fun-verify would have to guess: does D1b promote alone (route 4 just records the trigger for later), or do both promote simultaneously (violating one-variable-at-a-time), or does route 4 override route 2?
REFUTATION: The routing table is not a mutually-exclusive priority list. Routes 1-3 form the primary partition (what promotes next), while routes 4-6 are independent signals that fire alongside whichever primary outcome applies. The spec already resolves the claimed overlap through three mechanisms: (1) Deliberate language distinction -- route 2 says "promotes AUTOMATICALLY" while route 4 says "named trigger fires," using the same "fires/recorded" pattern as routes 5 and 6 (which nobody would claim conflict with routes 1-3). (2) Explicit sequencing -- the spec states the Challenger is "its own increment, fairness ladder mandatory" (line 55-57) and the PARKING_LOT says "ships in its own post-A2 increment" (line 244-246). A trigger firing records the condition as met for that future increment; it does not promote now. (3) The project's one-variable-at-a-time principle (PARKING_LOT line 83, Attribution fork verdict "A2 ships ALONE") makes co-promotion architecturally forbidden -- a project-level law that governs all routing tables. Prior routing applications confirm this pattern: the D1 fun-verify evaluated D1b's trigger independently as a recording mechanism ("NOT yet: its trigger did not fire"), and the fifth fun-verify applied multiple parallel signals alongside a single primary promotion. The proposed fix restates what the spec already communicates.

### R7 [moderate/design]
CLAIM: The spec asserts 'Scope (one variable: threat; economy ships NOTHING here)' (line 37) but section 5 introduces drop_gradient -- a position-based multiplier on drop amounts that changes the REWARD RATE at different depths. This is a second independent variable (incentive structure) bundled with the first (threat). Q3 'did bank-or-push-deeper change' cannot attribute its verdict: if the owner plays deep and Q3 moves, it could be because (a) the walk back is now contested (threat working) or (b) deeper kills are richer so there is more reason to push (gradient working). The preamble's 'if you never went deeper, say so' only disambiguates when the owner stayed shallow. In the deep-play case the experiment is confounded.
REFUTATION: The spec's "one variable" (line 37) refers to the "threat/pull" SYSTEM, not to "threat alone." The spec's own title (line 1) is "A2 ? Threat/pull economy (priority targeting + position pressure + leash + gradient)" ? the gradient is explicitly named as one of the system's four mechanisms. The brainstorm fork "depth = minimal in-map gradient (data-level)" (PARKING_LOT line 231) was a distinct owner fork decision, making gradient a designed component of A2, not scope creep.

"Economy ships NOTHING here" means D1b spending code (inscription, fees, priced sustain) ? see line 288 which explicitly defines it as "Economy code of any kind (D1b...)". The gradient modulates drop AMOUNTS by position; it does not add spending mechanics. These are different concepts in this project's vocabulary.

Q3 (line 255) deliberately names ALL three factors: "denser and richer, and the walk back is contested." It is not attempting single-mechanism isolation. The routing logic (lines 271-283) treats Q3 as a binary aggregate signal ("Q3 moved" ? system wins) and does NOT require sub-variable attribution. Q2/Q4/Q5 independently isolate threat sensation (pressure ring, contested corridor, wipe weight) without any gradient involvement ? that is where threat-specific signal lives.

Furthermore, threat without pull would make Q3 impossible to move positively: more danger for the same reward at depth means "bank" is always rational, making the chore worse. The dilemma requires both a cost (threat) and a reason (gradient/pull). The spec understands this ? that is why the system is named "threat/pull" and why the gradient is inseparable from the one-variable claim.

### R8 [critical/fun]
CLAIM: The D1 design invariant (world.rb:734 comment: 'the run back must always be possible') was calibrated for an UNOPPOSED corridor. A2 doubles human density (7 to 14) and makes the corridor live, but the spec inherits the same grace (2700f) without recalibrating or explicitly relaxing the invariant. Concrete failure: blocker step_frames=19 is SLOWER than rusher step_frames=16, so chasers CATCH the pack; with 5 engaged (engaged_cap) dealing 60 dmg/92f against a 300 HP freshly-respawned pack traversing ~40 tiles of hostiles, the pack absorbs ~500-700 damage in a deep-band recovery ? far exceeding total HP. The spec neither raises grace, nor adds a piloting gate for opposed-recovery feasibility, nor explicitly states deep wipes are intentionally unrecoverable.
REFUTATION: The finding is refuted on multiple grounds:

1. **Tab-swap defeats the damage scenario.** The finding's central mechanic ? "blocker step_frames=19 is SLOWER than rusher step_frames=16, so chasers CATCH the pack" ? is true only for the blocker. The player can Tab-swap to the striker (step_frames=13), which OUTPACES all enemies. The non-possessed bodies engage and potentially die, but the possessed striker is uncatchable. The AiController (controllers.rb:88-89) makes non-possessed pack members follow when nothing is in aggro range, meaning once past enemies the pack reconsolidates. The damage scenario (5 engaged dealing 60 dmg/92f against a standing pack) requires the player to sit on the blocker without swapping, dodging, or retaliating ? an unrealistic assumption stack.

2. **The D1 spec itself already calibrated against OPPOSED recovery.** The D1 corpse-run spec (line 114-115) says: "against the measured 30-45s opposed recovery it yields margin ~0.5-0.67." The finding claims the grace was "calibrated for an UNOPPOSED corridor," but the D1 spec's own math explicitly factors in opposition from existing respawning humans. The "2.2x worst-case unopposed run-back" describes the grace floor; the TERM calibration already accounts for fighting.

3. **Grace deferral is explicit methodology, not an omission.** The A2 spec (line 63, 293-294) says "no term/grace retune (parked until measured margins)." The scope contract (CLAUDE.md:38) locks values "until measured term_left/term margins exist." The spec's methodology (line 67) states all values "are HYPOTHESES, reset by pilot + telemetry, never by feel." Demanding pre-calibration before measurement violates the spec's own design method.

4. **The spec provides a piloting gate for recovery feasibility.** Fun-verify Q4 ("was the recovery ever in doubt ? did the corridor fight back this time?") + gate script act 4 ("a carrying death deep + contested run-back") are the designed instruments to surface if the grace becomes inadequate. The pre-registered routing (line 279) includes "Threat NOT felt ? tuning iteration (thresholds, density, cap ? data only)." The spec has a measurement-then-adjust pipeline.

5. **Time math works even worst-case.** The blocker crosses the full 42-tile district in 798 frames. Grace is 2700 frames ? a 3.4x margin. Even accounting for fighting delays, this leaves enormous headroom. On the striker (the natural run-back choice), it is 546 frames ? a 4.9x margin.

### R9 [moderate/fun]
CLAIM: Hate-tagged rushers respawn at 300f (spec: same kit, no override) while taunt cooldown is 600f, creating a 300f unprotectable window every cycle. In that window 3-4 hate rushers deal 12 dmg each to the 60 HP lobber (kill in ~138f / 1.5 attack cycles). This makes lobber death deterministic in every engagement that outlasts one taunt duration, collapsing the spec's '3-to-2-to-1 tension ramp' into an instant 2-body state within the first 5 seconds of any cluster encounter. Combined with lowhp_switch_pct=0.35 (threshold 21 HP), once the lobber takes ANY hate damage in the unprotected window, all other non-taunted humans also pile on ? overkill stacking that wastes the ramp entirely.
REFUTATION: The finding is refuted on three independent grounds:

1. CONTRADICTS LOCKED DESIGN INTENT. PARKING_LOT.md line 229 records a closed brainstorm fork verdict: "death cadence = wipes rare+heavy, body attrition stays frequent (the 3->2->1 spiral is the tension ramp)." The lobber being killable during the unprotected window IS the intended tension model. The finding frames an intended design feature as a defect.

2. GEOMETRIC IMPOSSIBILITY OF THE RESPAWN-CHAIN SCENARIO. The spec's respawn_block_tiles (12) exceeds the rusher's aggro_tiles (10), and the lobber follows the blocker at FOLLOW_DISTANCE=2 (controllers.rb:75). When the pack is far enough from a spawn for respawn to fire (>12 tiles), the lobber (~2 tiles from the blocker) is also >10 tiles from the spawn point -- outside the hate rusher's aggro range. The freshly respawned rusher cannot acquire the lobber as a hate target. The "300f respawn feeds instant hate engagement" chain the finding depends on is blocked by this near-total geometric overlap between the suppression radius and the aggro radius.

3. TAUNT IS NOT THE SOLE DEFENSIVE TOOL (finding misframes the problem). The spec's teaching beat is "protect the artillery" (line 81) -- an active multi-tool skill test. The blocker's basic attack has knockback (1 tile, arc3), the lobber has projectile retreat AI (retreat_step fires when chebyshev < 2, and its step_frames=16 completes before the rusher's 20f windup resolves, causing a miss), the player can physically interpose the 160HP blocker, and the pack can kill hate rushers during the 300f taunt window. The finding's "deterministic lobber death" requires ignoring ALL of these.

Additionally, the lowhp_switch_pct claim is overstated: 0.35 * 60 HP = 21 HP threshold requires 4 unmitigated hits (48 damage) before the cascade fires, not "ANY hate damage" as stated. And all spec values are explicitly marked as "HYPOTHESES, reset by pilot and telemetry, never by feel" (spec line 67) -- the pilot process exists precisely to catch degenerate timing windows if the geometry above is wrong in practice.

### R10 [moderate/fun]
CLAIM: The routing (line 271-283) declares 'A2 wins' on any Q3 positive without conditioning on contacts_en_route. This means A2 can be verified as a success while the corridor mechanism has zero impact (contacts_en_route = 0, same as 5 prior verifies), masking a non-functional mechanism. The fun thesis is 'threat must contest... the corpse they run back to' ? half the thesis goes untested in the happy-path branch. This is the same failure pattern that afflicted the ledger (system fired per telemetry, but wasn't felt per owner ? detected only because Q6 escape-valve existed).
REFUTATION: The defect does not exist because the spec already handles corridor non-contribution through three redundant channels, and the proposed fix would not change what gets built or decided.

(1) Q4 ("did the corridor fight back this time?") is ALWAYS asked regardless of Q3's answer ? the fun-verify collects all 8 answers first, then applies routing mechanically. The corridor signal is never skipped or lost.

(2) contacts_en_route is always recorded in telemetry (spec line 184-186: "the live-corridor contest measure; five verifies of 0 contested is the baseline to beat"). This metric is harness-computed from the event log, independent of routing decisions.

(3) The corridor is explicitly EMERGENT, not a distinct ship-gate mechanism. The spec states "NO corpse-specific code" (line 44) and "corpse-system changes (live corridor is emergent, by design)" (line 293). It is a byproduct of mechanisms 3+4, not a testable unit with its own acceptance criterion.

(4) The ledger analogy is categorically inapt. The ledger failure was a VISIBILITY defect (system fired, player never saw it ? Q6 "never saw any of it" blocked the verdict). The hypothetical corridor gap is a CONTRIBUTION question (one emergent path of six mechanisms didn't fire, but the player's overall experience improved). The first blocks evaluation; the second is a tuning signal ? which is exactly what the telemetry + Q4 recording already provide.

(5) Under both the current routing and the proposed fix, the downstream outcome is identical: A2 wins, the corridor non-contribution is on record (via telemetry + Q4 answer), and D1b-inscription is queued as the next candidate (line 272-273). The sub-clause adds verbiage to a mechanical routing table without altering any build decision or scope gate.
